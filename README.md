# AirRadar — акустическое обнаружение БПЛА

Пассивное обнаружение дронов по звуку одного микрофона. Целевые условия: лес,
близость ЛЭП, максимальная дальность. Пеленгация (азимут) — отдельная ветка на
GCC-PHAT по 4 каналам, нейросеть в ней не участвует. Архитектура системы
описана в [plan.md](plan.md).

Текущий этап: **бинарный детектор «дрон / не дрон» по одному каналу.**
Классификация типа (FPV / самолёт / промышленный) не реализована — см. раздел
«Чего нет».

---

## Главный вывод

Три раза подряд метрика показывала 0.99 и три раза это оказывалось враньём.
Ниже — история каждого случая. Это самая ценная часть документа: если браться
за задачу заново, время уйдёт именно на эти грабли, а не на архитектуру сети.

### 1. Утечка по частоте дискретизации (Kaggle DroneAudioDataset)

Класс однозначно определялся форматом файла:

| | drone | no_drone |
|---|---|---|
| частота | 22050 Гц | 16000 Гц |
| длина | 0.5 с | 4.0 с |

Сеть читала артефакты ресемплинга, а не звук. Лечение: всё приводится к
16 кГц моно и режется на окна фиксированной длины 0.5 с ([prep_dads.py](prep_dads.py)).

### 2. Синтетика Griffin-Lim

6000 из 7462 записей дрона (79%) в Kaggle-наборе — файлы `mel_*_gen*.wav`,
восстановленные из mel-спектрограмм. Фаза у них искусственная.

```
синтетика:          AUC = 1.0000
реальные записи:    AUC = 0.9189
```

AUC ровно 1.0 не бывает на честной задаче. Модель ловила артефакты генератора.
После выброса синтетики честный recall при FAR 1% оказался **56.8%**, а не 96%.

### 3. Слишком лёгкие негативы (DADS)

Негативы DADS — лай собак, детский плач, дверные звонки. Задача вырождается в
«стационарный гул или нет». Проверка [diag_leak.py](diag_leak.py): пять
признаков, физически не способных отличить дрон от бензопилы (громкость, ZCR,
спектральный центроид, плоскостность, разброс), дали **AUC 0.9844** против
0.9934 у свёрточной сети на 287k параметров.

### 4. Метрика, насыщенная в потолок

AUC на val DADS упирается в 0.99 у любой модели и перестаёт их различать.
Различает только измерение на трудных негативах **при зафиксированном recall**
([diag_compare.py](diag_compare.py)).

## Что установлено твёрдо

Единственное честно измеренное утверждение: **сеть выучила гармоническую
структуру моторов, а не громкость.**

При одинаковом recall 90%, на удержанных негативах (пересечение с обучающей
выборкой 0.1%, проверено точным сравнением окон):

| категория | CNN | тривиальный baseline |
|---|---|---|
| vacuum_cleaner | 0.0% | 9.1% |
| engine | 0.0% | 6.8% |
| chainsaw | 3.1% | 10.9% |
| engine_idling | 1.3% | 5.3% |
| thunderstorm | 0.3% | 3.1% |
| **средняя по трудным** | **0.7%** | **2.2%** |

Разница втрое-вдесятеро в пользу сети. Случайностью это быть не может.

### Обратная сторона: ветер

| | CNN | baseline |
|---|---|---|
| wind | **5.6%** | 0.3% |

Сеть путалась на ветре в двадцать раз чаще примитива. Причина — в аугментации:
шум подмешивался при SNR до −12 дБ, а на −12 дБ в окне 0.5 с дрона физически
не слышно. Пример состоял почти целиком из шума, а метка говорила «дрон», и
сеть честно выучила, что широкополосный шум и есть признак дрона.

Исправлено: нижняя граница SNR поднята до −6 дБ, трудные негативы добавлены в
обучение. Дальность берётся не выкручиванием SNR, а накоплением по нескольким
окнам подряд ([detect.py](detect.py), правило «k из m»).

## Итоговые числа

Модель `dronenet.pt`, обучение остановлено на 8-й эпохе из 15 — дальше метрики
насыщались и перестали различать чекпоинты.

На val DADS: **AUC 0.9980**, recall **98.9%** при FAR 1%, recall 95.8% при FAR 0.1%.
Верить этим числам как предсказанию поля нельзя, см. раздел «Главный вывод».

Ложные срабатывания на удержанной половине `cache_hard` (23 817 окон, порог по
рабочей точке FAR 1%), до и после добавления трудных негативов в обучение:

| категория | до | после |
|---|---|---|
| wind | 10.3% | **0.0%** |
| vacuum_cleaner | 0.0% | 0.0% |
| engine | 0.0% | 0.0% |
| rain | 0.3% | 0.0% |
| thunderstorm | 1.2% | 0.0% |
| helicopter | 3.5% | 3.2% |
| airplane | 5.6% | 6.2% |
| chainsaw | 8.8% | **10.0%** |
| **средняя по трудным** | 1.8% | **1.1%** |
| **recall при FAR 1%** | 96.3% | **98.9%** |

Провал на ветре вылечен полностью — подтверждение диагноза про SNR −12 дБ.

`chainsaw` осталась худшей строкой и слегка ухудшилась. Это не дефект обучения:
бензопила — двухтактный мотор с выраженными гармониками, акустически ближайший
к дрону объект во всём наборе. Туда же `airplane` и `helicopter` — винтовая
авиация. Устранять это без риска потерять сами дроны, скорее всего, нельзя;
разумнее закрывать накоплением по времени и, позже, пеленгацией.

**Оговорка.** Удержанная половина `cache_hard` — это другие клипы тех же
категорий, записанные теми же микрофонами, что и обучающая половина. `wind 0.0%`
отчасти означает «выучила эти конкретные записи ветра». Поведение на реальном
ветре в кронах остаётся непроверенным.

## Полевые записи — первая проверка на реальном дроне

Две записи грузового дрона (`field/drone_video.wav`, 48.2 с и
`field/drone_video2.wav`, 39.1 с). Разметка полная: моторы слышны всю запись.
Это единственная **ненасыщенная** метрика в проекте — на публичных данных всё
упирается в 0.99 за пару эпох, здесь модель либо слышит гармоники, либо нет.

Модель с `n_fft=512`, показавшая 98.9% на DADS:

| порог | `drone_video` | `drone_video2` |
|---|---|---|
| FAR 5% на трудных | 65.4% | 7.7% |
| **FAR 1% (рабочая точка)** | **24.1%** | **0.0%** |
| FAR 0.1% | 7.9% | 0.0% |

**98.9% на DADS против 24.1% и 0.0% в реальности.** Публичные записи — это
малые квадрокоптеры (Membo, Bebop) с близкой дистанции. Грузовой дрон для этой
модели — другой объект.

Спектрограммы ([spectrum.py](spectrum.py), картинки в `field/`) объясняют
причину двумя независимыми находками.

### Разрешение по частоте

Основные частоты полевых записей — **78 и 59 Гц**, гребёнка гармоник идёт
78/156/234/312 и 59/118/177/236/295 Гц. При `n_fft=512` шаг спектра 31.25 Гц,
и соседние гармоники разделены всего 2.2 бинами — гребёнка сливается в сплошное
пятно. У малого квадрокоптера основная ~200 Гц, там разделение 6.4 бина и всё
читается.

Признака просто нет в спектрограмме, сколько ни обучай. Исправлено переходом на
`n_fft=2048` (шаг 7.81 Гц, разделение 9 бинов). Вход сети при этом не меняется:
при `hop=128` кадров по-прежнему 63, mel-полос 64.

### Полоса гула ЛЭП совпала с дроном

Аугментация добавляла «гул ЛЭП» на 50/100/150/200 Гц амплитудой до 0.8 от пика.
Гребёнка второй записи — 59/118/177/236 Гц — ложится на эту сетку почти точно.
Модель училась, что энергия в этой полосе есть помеха, и пропускала грузовой
дрон целиком. Первая запись (78 Гц) отстроена от сетки лучше, отсюда 24.1%
вместо нуля.

Второй случай за проект, когда аугментация, добавленная из лучших побуждений,
стреляла в цель. Первым был SNR −12 дБ, научивший сеть считать широкополосный
шум дроном.

Совсем убирать гул нельзя — рядом с ЛЭП он будет. Различить можно по форме:
сетевая наводка это чистый стационарный тон ровно на 100.00 Гц, а дрон даёт
кластер шириной несколько герц из-за плавающих оборотов. При шаге 7.81 Гц
разница видна, если её не заглушать. Амплитуда снижена до 0.25.

### Поправка: вывод «n_fft=2048 не помог» был сделан на шуме

Первое сравнение (`compare_models.py`) показало recall 24.1% → 18.8% и было
прочитано как отрицательный результат. Это неверно. Блочный бутстрап
(`evalx/field_ci.py`) даёт на этой разнице 95% CI [−3.1, +8.4] пп — не значимо.
Хуже того: между соседними эпохами одного и того же прогона `recall_поле`
прыгает на 9 пп при монотонно растущем `auc_hard` — сама метрика дрожит сильнее
эффекта, который ей пытались измерить. Полный разбор — [docs/metrics-plan.md](docs/metrics-plan.md).

Честная метрика без пола — `AUC_fh` (полевые окна против трудных негативов),
не упирается в 0.0% там, где упирается recall:

| | `drone_video` (78 Гц) | `drone_video2` (59 Гц) |
|---|---|---|
| n_fft=512, гул 0.8 | AUC 0.950, медиана p 0.159 | AUC 0.716, медиана p 0.0075 |
| n_fft=2048, гул 0.8 | AUC 0.944, медиана p 0.567 | AUC 0.757, медиана p 0.0402 |
| **n_fft=2048, гул 0.25** | **AUC 0.945, медиана p 0.575** | **AUC 0.780, медиана p 0.0470** |

Монотонный рост на обеих правках подряд, именно на трудной записи. Обе правки
разводят гул и гребёнку дрона в признаковом пространстве, а не только по
частоте — см. следующий раздел.

### Причина: гул ЛЭП и гребёнка дрона — почти один вектор признака

Модельно-независимое измерение (`evalx/feat_visibility.py`): синтетический гул
ЛЭП (50/100/150/200 Гц) и гребёнка дрона 62 Гц в исходном лог-меле дают
**косинус 0.90** — сеть буквально не может их различить в признаке, который ей
подают. Аугментация подмешивает гул в оба класса и потому учит игнорировать
именно то подпространство, где целиком живёт тяжёлый дрон.

Узкое место — не разрешение STFT, а **раскладка mel-банка**: на 64 полосах от
20 до 8000 Гц ниже 300 Гц приходится всего 8, шириной ~31 Гц. Гребёнки 50 Гц и
62 Гц (и их гармоники) попадают в один и тот же набор полос независимо от
`n_fft`.

Первоначальный план сузить `FMAX` до 2000 Гц отклонён — это снесло бы 2–8 кГц,
где живёт лопастной шум малых квадрокоптеров, а детектор должен ловить все
типы. Следующий эксперимент: `n_mels=128` при `fmax=8000` (даёт те же 17 полос
ниже 300 Гц без потери верха), не проверено.

### Открытый вопрос: рабочая метрика

Recall при фиксированном FAR не подходит для сравнения конфигураций — он то
упирается в 0.0% (второй записи не хватает динамического диапазона), то
дрожит на ±9 пп между соседними эпохами. Взамен предложена (не внедрена)
метрика **SNR50** — порог SNR, при котором обнаружение падает до половины;
не насыщается конструктивно. Подробности и полный приоритетный план работ —
[docs/metrics-plan.md](docs/metrics-plan.md).

Отдельная находка того же разбора: правило «k из m» на текущих данных **не
поднимает дальность, а снижает** — при равном пооконном FAR 1% recall 24.1%
превращается в 12.4% времени под тревогой. Правило выигрывает только при
калибровке порога на уровне решения (FA/час), которой в проекте пока нет.

### Две ловушки при разбиении

**Группировка.** Имена в DADS обрезаны, источник записи потерян. 163k клипов по
0.6 с нарезаны всего из 6 датасетов, значит соседние номера — куски одного
полёта. Случайный сплит растащил бы их по train и val. Группируем блоками по
250 номеров (`BLOCK` в [prep_dads.py](prep_dads.py)). Это приближение: одна
длинная запись занимает несколько блоков и всё ещё может попасть в обе части.
Точная группировка требует маппинга номер → исходный файл, которого нет.

**Разбор имён ESC-50.** Клипы порезаны на 5 сегментов, номер сегмента дописан в
конец поля target: `362` = target 36, сегмент 2. У target 0 поле вырождается в
одну цифру (`3` = target 0, сегмент 3). Наивный `int(поле)` даёт случайную
категорию — баг ловится `prep_hard.py --selfcheck`.

## Архитектура

**Признаки.** Лог-мел спектрограмма 64 × 63, окно 0.5 с при 16 кГц,
`n_fft=2048`, `hop=128`, полоса 20–8000 Гц. Считается через `torch.stft` на GPU,
mel-фильтры написаны руками — `torchaudio` не нужен.

**Модель.** `DroneNet`, 287k параметров: три блока по два свёрточных слоя
(32/64/128 каналов) с BatchNorm и MaxPool, global average pooling, один логит.
Держим маленькой ради работы на слабом железе в поле.

**Аугментация** — вся на GPU, батчем. Смысл: «отодвинь цель дальше».

| шаг | параметры | зачем |
|---|---|---|
| циклический сдвиг | случайный | позиция не должна быть признаком |
| подмешивание фона | SNR от −6 до +15 дБ | главный фактор дальности |
| затухание верхов | `exp(-k·f·d)`, k до 2.5 | поглощение воздухом и листвой |
| гул ЛЭП | 50 Гц + 3 гармоники, амплитуда до 0.25 | работа рядом с ЛЭП |
| пиковая нормализация | — | громкость не признак класса |
| SpecAugment | 2 маски по частоте и времени | регуляризация |

Notch-фильтр на 50 Гц из [plan.md](plan.md) в обучении не используется: гул
подмешивается аугментацией, и сеть учится его игнорировать. Для ветки
пеленгации notch по-прежнему нужен — там важна фазовая структура.

**Отбор чекпоинта** — по `auc_hard` (дрон против механического шума и погоды),
не по AUC на val DADS: вторая упирается в 0.99 и не различает модели.

**Решение в реальном времени** принимается не по одному окну, а по правилу
«k из m» — по умолчанию 4 окна из 6 подряд, то есть 1.5 с. Порыв ветра даёт
одиночные выбросы вразнобой и отсекается; дрон приближается секундами и даёт
устойчивую серию. Этот же механизм честно поднимает дальность.

## Структура

```
prep_dads.py  prep_hard.py  train.py  eval.py     основной конвейер
detect.py     web.py        spectrum.py           инференс и разбор
diag_leak.py  diag_hard.py  diag_compare.py       диагностика утечек

field/     полевые записи и их спектрограммы
models/    чекпоинты
logs/      логи прогонов
archive/   отработавшее: старый Kaggle-кэш, ранние эксперименты

DADS/  DroneAudioDataset/  cache_dads/  cache_hard/    данные (~20 ГБ)
```

| файл | назначение |
|---|---|
| [prep_dads.py](prep_dads.py) | DADS parquet → `cache_dads/` |
| [prep_hard.py](prep_hard.py) | негативы с категориями → `cache_hard/` |
| [train.py](train.py) | обучение, аугментация, модель |
| [eval.py](eval.py) | recall при заданном FAR + ложные по категориям |
| [detect.py](detect.py) | реальное время с микрофона, правило «k из m» |
| [web.py](web.py) | веб-интерфейс: живое обнаружение + прогресс обучения |
| [spectrum.py](spectrum.py) | спектрограммы полевых записей, поиск гребёнки |
| [diag_leak.py](diag_leak.py) | дубликаты, ближайший сосед, тривиальный baseline |
| [diag_hard.py](diag_hard.py) | пересечение `cache_hard` с обучающей выборкой |
| [diag_compare.py](diag_compare.py) | CNN против baseline при одинаковом recall |

Каждый скрипт имеет `--selfcheck` — проверку логики без данных.

В `archive/` лежит отработавшее: `data_prep.py` и `cache_kaggle/` (старый
Kaggle-набор, строгое подмножество DADS), `test1-3.py` — ранние эксперименты,
из них [test3.py](archive/test3.py) содержит проверку математики GCC-PHAT на
симулированных 4-канальных данных. `cache_kaggle/` занимает 933 МБ и больше не
нужен — можно удалить.

## Окружение

RTX 4050 Laptop 6 ГБ, torch 2.12.0+cu130, драйвер 580.173.02, 15 ГБ RAM.

### Машина без GPU

Для чтения кода, правок и прогона `--selfcheck` карта не нужна: `DEV` в
[train.py](train.py) сам падает на `cpu`. Полное колесо CUDA весит 2,5 ГБ и
на такой машине бесполезно, поэтому ставится сборка под CPU:

```bash
pip install pyarrow huggingface_hub
pip install torch --index-url https://download.pytorch.org/whl/cpu
```

Обучать так нельзя — только проверять код. Сам прогон идёт в Colab, см.
раздел «Обучение в Colab» в [RUNBOOK.md](RUNBOOK.md).

Кэш `cache_dads` (5.1 ГБ) в оперативную память целиком не помещается, поэтому
читается через `np.memmap`; индексы батча сортируются ради локальности доступа.

Обучение уже идёт на GPU полностью — модель, лог-мел через `torch.stft` и вся
аугментация. Узкое место не вычисления, а дисковый ввод-вывод.

При ошибке CUDA `Error 804: forward compatibility was attempted on non supported
HW` сверить `/proc/driver/nvidia/version` с версией NVML из `nvidia-smi`:
расхождение означает, что драйвер обновился без перезагрузки. Лечится
перезагрузкой, выгрузить модули на живой системе не выйдет — их держит X-сервер.

## Чего нет

**Классификации типа дрона.** Ни в DADS, ни в Kaggle-наборе нет меток
FPV / самолёт / промышленный — только 0/1. Разметку придётся делать самим.

**Пеленгации.** Математика GCC-PHAT проверена на симулированных 4-канальных
данных ([test3.py](archive/test3.py)), в систему не интегрирована.

**Полевой проверки.** Все числа получены на публичных датасетах — записях с
близкой дистанции в тепличных условиях.
