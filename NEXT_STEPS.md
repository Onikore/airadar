# Дальнейшие шаги

Актуально на чекпоинт `models/dronenet.pt` (n_fft=2048, гул 0.25, отобран по
`auc_hard` на эпохе 10). Контекст и обоснования — [README.md](README.md) и
разбор методологии — [docs/metrics-plan.md](docs/metrics-plan.md), тут только
список дел по приоритету.

---

## Шаг 0 — сделать сравнения осмысленными (0.5 ч, без GPU)

Сейчас чекпоинт отбирается по `auc_hard`, которая насыщена и превращает выбор
эпохи в лотерею (±9 пп на `recall_поле` между соседними эпохами одного
прогона). Пока это не зафиксировано, следующие эксперименты снова будут
сравнивать шум с шумом, как уже было с `n_fft=512` против `2048`.

Сделать одно из двух: всегда брать последнюю эпоху, либо усреднять веса
последних трёх. Править в [train.py](train.py), функция `main`.

---

## Шаг 1 — дешёвая диагностика без переобучения (3–4 ч, без GPU)

Три скрипта в [`evalx/`](evalx) уже частично готовы (`feat_visibility.py`,
`field_ci.py`, `f0_survey.py`). Добавить:

**D1. Отклик на гул** (5 мин). Взять полевые окна, которые модель сейчас ловит,
добавлять синтетический гул амплитудой 0→0.8, смотреть, при каком уровне
`p` обваливается. Контроль — то же на окнах DADS с f0≈200 Гц.

**D2. Развёртка по f0 ресемплингом** (30 мин). Растянуть/сжать обе полевые
записи в 0.7–1.8 раза, построить `p(f0)`. Провал ровно на 50/100/150/200 Гц —
подтверждение коллизии с гулом; монотонный спад без провалов — вопрос
разрешения; плоско и низко — модель не пользуется низом вообще.

**D4. Окклюзия по mel-полосам** (1 ч). Обнулять по одной полосе, смотреть
падение `p`. Отвечает на прямой вопрос: держится ли нынешний recall на низах
или на верхних гармониках, которые для тяжёлых машин не показательны.

Результат определяет шаг 2.

## Шаг 2 — конфигурация признака (1 ч перебор + 40 мин на выбранный вариант)

Кандидат по текущим данным (`evalx/feat_visibility.py`, косинус гул/дрон,
таблица в README): **`n_mels=128` при `fmax=8000`** — даёт 17 mel-полос ниже
300 Гц вместо 8, без потери верха, где живёт лопастной шум малых
квадрокоптеров (в отличие от отклонённого варианта `fmax=2000`).

Перед прогоном на GPU прогнать `feat_visibility.py` по сетке `n_fft × n_mels ×
fmax`, чтобы не тратить 40 минут на конфигурации, заведомо худшие по
модельно-независимой метрике видимости гребёнки.

Требует правки `N_MELS` в [train.py](train.py); входной размер сети изменится
(сейчас 64×63), `DroneNet` подхватит автоматически через global average pool.

## Шаг 3 — правило принятия решения (0.5–1 день)

Находка из `docs/metrics-plan.md`: «4 из 6» на текущих данных **снижает**
recall (24.1% → 12.4% времени под тревогой при равном пооконном FAR), потому
что срабатывания недостаточно сгруппированы во времени для этого порога.

Проверить дешёвого конкурента: скользящее среднее логита по m окнам с порогом,
вместо бинаризации-до-накопления. Ожидаемый выигрыш из плана — 2–4 дБ по
дальности. Правка в [detect.py](detect.py) и [web.py](web.py).

Калибровать после этого — на непрерывном фоновом корпусе (шаг 4), не на две
полевые записи.

## Шаг 4 — непрерывный фоновый бенчмарк (1 день)

Строится из того, что уже на диске, без новых записей:

- UrbanSound8K, трудные классы (air_conditioner, drilling, engine_idling,
  jackhammer) — 4.19 ч непрерывного фона по 4 с на клип.
- ESC-50 в `DroneAudioDataset/no_drone` — клипы порезаны на 5 сегментов по 1 с,
  склеиваются обратно однозначно (проверено на всех 2000). Трудные категории —
  40 минут, включая chainsaw, helicopter, airplane, wind, rain, thunderstorm.

Даёт операционную тройку `(FA/час, P(тревога за 10 с), медианное время до
тревоги)` вместо recall при произвольном FAR — README после этого шага
переписывается под эту тройку.

---

## Шаг 5 — SNR50 и f0-страта (1 день на харнесс, потом 5 мин/модель)

Главная метрика проекта на будущее. Параметризованная лестница деградации
(SNR от +20 до −15 дБ, частотное затухание, опционально гул) поверх полевых
записей и низкочастотной страты DADS (~21 600 окон дрона с f0 < 100 Гц, уже на
диске, требует валидации по нечётным гармоникам — полчаса). Скаляр — SNR, при
котором обнаружение падает до 50%. Не насыщается никогда, единица физическая
(6 дБ ≈ ×2 дальности).

С этого момента модели сравниваются по SNR50, а не по recall на двух записях.

## Шаг 6 — полевой выезд (2–3 дня)

Цель — метрика **d50** (дистанция 50%-го обнаружения при 1 FA/час на фоне той
же площадки). Делать после шагов 0–5, иначе третий раз потратим выезд на то,
что можно было решить на столе.

Обязательный протокол:

1. **Фон первым** — 6–8 ч, та же цепочка микрофон/преамп/усиление, что пойдёт
   в эксплуатацию. Рассвет, день, ветер, дождь, отдельно под ЛЭП и в 200 м.
2. **≥50 пролётов**, ≥3 типа машин (грузовой / средний квадрокоптер / малый
   FPV), радиальные уходы от микрофона до предела связи — один уход даёт всю
   психометрическую кривую дистанций, а не одну точку.
3. **Телеметрия вместо ручной разметки** — GPS-лог дрона плюс синхронизация
   часов (хлопок или тональный маркер в начале и конце сессии). Метка
   становится непрерывной (дистанция, азимут, высота), а не бинарной.
4. **4 канала сразу** — даже если пеленгация ещё не подключена, второй выезд
   за тем же стоит дня.
5. Делить по пролётам и дням, не по окнам. Одну площадку и один тип машины
   отложить целиком до финальной проверки — единственный способ получить
   число, которому можно верить в отчёте.

## Отдельно, не блокирует остальное

- **Типы дрона (FPV/самолёт/промышленный).** Меток нет ни в одном публичном
  датасете. Реалистично только после шага 6 — размечать по логу телеметрии.
- **Пеленгация.** Математика GCC-PHAT проверена на симуляции
  ([archive/test3.py](archive/test3.py)), в систему не интегрирована. Не
  зависит от шагов 0–5, можно вести параллельно.
- **`archive/cache_kaggle/`** (933 МБ) можно удалить в любой момент — не
  используется с момента перехода на DADS.
